# Deployment and operations

## Destination

The checked-in `Dockerfile` and `render.yaml` deploy **one paid Render web service with a persistent disk**. Docker can also run on another host that supplies HTTPS, one persistent `/data` volume and the same environment variables. No paid resource is provisioned by this repository or by CI. Automatic production deploys are disabled in the Blueprint.

The operator currently has no hosting/email/backup accounts. Complete the setup below; no secrets should be pasted into chat or committed to Git.

## Required services and values

| Service/value             | What to prepare                                                                                                                                                                                                                                                                                                                                          |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Render                    | Connect this GitHub repo, choose the branch containing the production implementation, and create a Blueprint from `render.yaml`. Review its paid service/disk before deploying. Keep one instance and `/data/quad.sqlite`.                                                                                                                               |
| Verification email        | An SMTP provider with a verified sender/domain, SMTP host/user/password, and TLS port 587 (or port 465 with `SMTP_SECURE=true`). Set `MAIL_FROM` to its approved sender. Test delivery to a real Rutgers inbox and configure the provider's SPF/DKIM records.                                                                                            |
| Support and moderation    | A monitored `SUPPORT_EMAIL`. Set `ADMIN_EMAILS` to approved Rutgers school emails for the actual moderators. Admins still verify their own inboxes normally. Reports appear in Profile → Moderation; generic notifications go to these emails without report details.                                                                                    |
| Encrypted offsite storage | A private S3-compatible bucket, region, optional endpoint (e.g. for Cloudflare R2), and credentials restricted to that bucket's `quad/` prefix. Allow PutObject, GetObject for recovery, DeleteObject and ListBucket on that prefix. `BACKUP_KEY` is generated by the Blueprint; save a recovery copy separately. Losing it makes backups unrecoverable. |
| Origin                    | Render supplies `RENDER_EXTERNAL_URL`, used by default. For a custom domain set `APP_ORIGIN=https://your-domain` without a trailing slash. Cookies and mutations require that exact browser origin.                                                                                                                                                      |
| Auth secret               | The Blueprint generates `AUTH_SECRET`. Keep it private. Changing it invalidates outstanding verification codes; revoke sessions separately if compromise is suspected.                                                                                                                                                                                   |
| Map tiles                 | The Blueprint uses OpenStreetMap standard tiles with visible attribution, browser caching, no offline prefetch and normal interactive requests. Follow its usage policy. Configure `MAP_TILE_URL` and `MAP_ATTRIBUTION` for a suitable hosted provider before higher traffic; restrict any public browser key by your deployed origin.                   |

Production startup rejects missing service values, weak secrets, unapproved school-domain configuration, insecure origins, and a database path outside `/data`. This validates configuration, not actual external delivery or storage access. Set `TRUST_PROXY=1` only behind Render's controlled proxy; direct deployments should leave it off unless configured for their proxy.

Official references: [Render Blueprints](https://render.com/docs/blueprint-spec), [persistent disks](https://render.com/docs/disks), [OSM tile usage policy](https://operations.osmfoundation.org/policies/tiles/), [Expo builds](https://docs.expo.dev/build/introduction/).

## Web deployment sequence

1. Create the services above and configure credentials in the hosting dashboard. Do not add `.env` to Git.
2. Deploy the reviewed commit using the Blueprint. Keep the disk when redeploying. Container startup drops privileges to the `node` user after preparing the disk.
3. Migrations apply transactionally before listening. The production image contains no legacy demo server or test mail-capture server. Verify `/healthz`, then `/readyz`. The first encrypted offsite backup starts shortly after boot; `lastSuccess` must become a timestamp.
4. Run `node scripts/smoke-live.mjs https://YOUR-APP`. This checks unauthenticated isolation, demo-login exclusion, policy pages, security headers and recorded backup success. It never sends a sign-in email.
5. Verify a real school inbox, complete onboarding with a new account, and check another independent account. Do not use test fixtures with real students.
6. Test requests/acceptance, received chat, private linkup invitations, public RSVP, blocking, reporting, moderator notification/queue, suspension, logout and deletion. Test sharing from a phone on campus, then Ghost Mode, permission revocation, expiry, background/resume and offline behavior. Online revocation becomes visible on the next poll (normally within 10 seconds); offline maps hide markers on a failed refresh and after their expiry.
7. Review the published terms/privacy pages and ensure the operator can honor them. Staff moderation, monitor provider quotas and disk use, and test a backup recovery before inviting a pilot cohort.

## Native builds and distribution

The same API supports the native app. The web deployment is a prerequisite for a release API origin.

1. Create/sign into the operator's Expo account. Run `npx eas-cli init` from `apps/mobile` to link an Expo project. Accept any account/service terms yourself.
2. Choose/check ownership and availability of the iOS bundle identifier and Android package in `app.config.ts` **before** the first store upload. The current candidate is `com.quadcampus.app`.
3. In EAS preview and production environments, set `EXPO_PUBLIC_API_URL` to the deployed HTTPS API origin (no trailing slash). Never put backend secrets in `EXPO_PUBLIC_*` variables.
4. For Android, set `ANDROID_GOOGLE_MAPS_API_KEY` and restrict it to the final package and signing certificate using the map provider's console. The build fails if this is missing. iOS uses Apple Maps.
5. Run `npx eas-cli build --profile preview --platform android` for an internal APK, or the iOS equivalent after configuring signing/devices. Run real-device tests for email sign-in, location permissions, map, chat and background handling. JS export success alone does not prove the installed binary works.
6. Production builds use `npx eas-cli build --profile production --platform all`. Native signing, Apple/Google developer accounts, privacy/data-safety declarations, age rating, moderation/contact details, policy URLs, review access and store submission require the operator's accounts. No store submission has been made.

Native production tokens use SecureStore. Browser sessions use secure HTTP-only host-only cookies. No refresh token or backend secret is placed in client storage.

## Backups and recovery

The backend snapshots SQLite using the online backup API, encrypts it with AES-256-GCM and uploads under `quad/` every six hours. It prunes its own encrypted snapshots after 30 days. The production bucket must remain private. Logs record success/failure without credentials or account content. Alert on failed backups and on `/readyz` showing a last success older than 24 hours. A Render disk snapshot is not a substitute for the database backup/restore procedure.

Recovery drill:

1. Download an encrypted snapshot from the private bucket using the storage console. Stop the app; do not restore over an active SQLite database.
2. On a trusted machine with Node and the repo dependencies, provide `BACKUP_KEY` through a secure environment and run:
   `node scripts/restore-backup.mjs downloaded.sqlite.enc NEW-DATABASE.sqlite`
3. The script refuses an existing target and verifies authentication and SQLite integrity. Keep the old database and its WAL files together for rollback. Point `QUAD_DB` to the restored file on the persistent disk, ensure ownership, then restart.
4. Validate profiles/connections/messages/events and optionally revoke all sessions with `DELETE FROM sessions` during an offline maintenance session. Recovery can restore records deleted after the snapshot: reconcile post-snapshot deletion requests before reopening. Backups can include a deleted account until retention expires.
5. Remove plaintext recovery copies from unencrypted temporary storage after validation. Keep a dated recovery-drill record outside the bucket.

## Operations and rollback

- Monitor `/healthz`, API error rate, SMTP failures/quotas, moderation queue age, `/readyz` backup age and disk capacity. Check the moderation queue even if email alerts fail. This version requires a human moderation operator.
- Presence stores only fixed approximate cells; cleanup clears stale/expired cells every minute. Raw GPS is not retained or logged. Other data retention is in the published privacy page and backend housekeeping code.
- Deploys with a disk have downtime; schedule the first pilot accordingly. Never scale to multiple replicas sharing SQLite. Back up before schema changes. Migration files are immutable once deployed and checksum-checked.
- For code-only rollback, deploy the previous image only when its schema is compatible. For a migration rollback, stop the service and use a verified backup and matching code; do not edit migration checksums to force startup.
- Keep the runtime and lockfiles updated; CI audits both dependency trees. The Expo fingerprint tool's minimatch dependency is overridden to patched v11 (build tooling only); native exports and fingerprint generation are verified after this change.
- Default caps: 500 discovered profiles per bootstrap, 500 relationships per account, 200 upcoming events per feed, 100 messages per chat page. Messages are fetched only for the active conversation, not downloaded in every bootstrap. Upgrade database/querying/pagination as the pilot grows.
